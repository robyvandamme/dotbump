## Scope of Changes

Replaces the hand-rolled argument pre-parsing (`ArgumentHandler`) with Spectre.Console.Cli's own lifecycle:

- `Program` no longer configures Serilog up front; it registers a new `DelegatingLogger`, an `ILogger` adapter that
  forwards `Write(LogEvent)` / `IsEnabled` to the current `Log.Logger` at call time.
- New `LoggingInterceptor : ICommandInterceptor` is set on the `CommandApp`. When Spectre invokes it, the bound
  `BumpSettings` (`--debug`, `--logfile`) are used to configure Serilog, *before* the command is created and resolved
  (so constructor-injected `ILogger`s in commands resolve the configured logger).
- `LoggerConfigurator.Configure` now takes `(bool debug, string? logFile)` instead of `args`.
- The `ArgumentHandler` pre-parser and its 254-line test file are deleted; the CLI-level syntax-acceptance test
  (`BumpSdkCommandTests`) is extended to cover the `--debug true/false` and `--logfile` argument forms.
- New tests: `DelegatingLoggerTests` (forwarding behavior incl. DIM-bound `Debug` convenience call) and
  `LoggingInterceptorTests` (debug on/off semantics, logfile content with startup diagnostics).

This removes ~100 lines of duplicated grammar logic that had to be kept manually aligned with Spectre's option parsing,
which is a genuine correctness simplification.

## Overall Assessment

A good, well-motivated refactor. The core insight — that Spectre builds its DI container before running interceptors,
so the registered logger must resolve the active logger lazily — is correctly handled and clearly explained in the XML
remarks. The alternative (keeping a fragile pre-parser) was a maintenance trap; this branch eliminates a whole class
of grammar-drift bugs instead of patching them.

Conventions are followed: file headers, file-scoped namespaces, primary constructor on `LoggingInterceptor`, Serilog
message templates without interpolation, `<inheritdoc/>`, and structured test naming. I verified that
`ArgumentHandler` has no remaining references (production or test), that Serilog 4.4.0's `ILogger` really is limited to
`Write`/`IsEnabled` with the remaining members as default interface implementations (so the `DelegatingLogger` surface
is sound for this package version), and that the `xunit.runner.json` setting (`parallelizeTestCollections: false`)
prevents the static `Log.Logger` manipulation in the new tests from racing — see non-issue 5 below.

No blockers. Findings below.

### 1. [Minor] The end-to-end settings→interceptor wiring is untested
`test/DotBump.Tests/Commands/BumpSdk/BumpSdkCommandTests.cs:525-558`

> **Resolution.** Covered by `test/DotBump.Tests/CommandConfigurationTests.cs`
> (`Configure.With_Debug_And_LogFile_Configures_Logging_Before_Command_Runs`). The test runs the production
> `CommandConfiguration.Configure(new DelegatingLogger(), versionInfo)` wiring rather than a hand-built registrar, so
> the interceptor registration itself is exercised. It executes
> `sdk --debug --logfile <temp>/app.log --file <temp>/missing.json`; the missing `--file` fails inside `SdkFileService`
> before any network call, keeping the test deterministic and offline. It asserts exit code `1` and that the rolled log
> file contains `Starting sdk` and `An error occurred while trying to bump the sdk`.
>
> The suggested snippet was adapted to this repository: `LocalDirectory.AbsolutePath` (not `.Path`), Shouldly (not
> FluentAssertions' `.Let`/`.Should`), `RegisterInstance` (not `RegisterFactory`), and a single handler registration.

The extended syntax-acceptance test runs a `CommandApp` configured manually, and critically this manual config does
**not** call `config.SetInterceptor(...)`. No test in the suite does. As a result:

- `LoggingInterceptorTests` proves the interceptor logic given already-bound settings.
- `With_Logging_Syntax_Accepted_By_Spectre_Returns_0` proves Spectre accepts the argument forms.

But nothing proves the two halves connect: that `CommandConfiguration.Configure` registers the interceptor, that the
bound `BumpSettings.Debug`/`LogFile` actually flow into it, and that the command's constructor-injected logger sees a
configured pipeline. A binding regression (e.g., an option name typo such that `Debug` stays `false`) would still make
every current test pass.

**Suggestion:** add one app-level integration test, e.g.:

```csharp
public async Task With_Debug_And_LogFile_Configures_Logging_Before_Command_Runs()
{
    using var logDirectory = new LocalDirectory("./temp");
    var logFile = Path.Combine(logDirectory.Path, "app.log");
    var app = new CommandApp();

    app.Configure(config =>
    {
        config.Settings.Registrar.RegisterInstance(testConsole);
        config.Settings.Registrar.RegisterInstance(handler.Object);
        config.Settings.Registrar.RegisterFactory<IBumpSdkHandler>(() => handler.Object);
        config.SetInterceptor(new LoggingInterceptor(new VersionInfo(typeof(LoggingInterceptor).Assembly)));
        config.AddCommand<BumpSdkCommand>("sdk");
    });

    await app.RunAsync(["sdk", "--debug", "--logfile", logFile]);
    await Log.CloseAndFlushAsync();

    Directory.GetFiles(logDirectory.Path, "app*.log")
        .ShouldHaveSingleItem()
        .Let(File.ReadAllText)
        .Should().Contain("Starting sdk");
}
```

This closes the loop between parsing, interception, and logging *before* command execution — the whole point of the
change.

### 2. [Minor] The `--logfile` path is never validated; sink failures are silent in Release
`src/DotBump/LoggingInterceptor.cs:42`

> **Resolution.** Accepted as a known limitation and documented, per the reviewer's "arguably out of scope" note.
> `README.md` (Logging section) now states that `--logfile` is not validated up front and that a file that cannot be
> created or written leaves the command running without producing a log or an error; `AGENTS.md` records the same in
> the Logging Flow notes so it is not "fixed" by reintroducing pre-parsing.
>
> One correction to the original analysis: Serilog.Sinks.File 7.0.0's `FileSink` constructor creates missing
> directories (`Directory.CreateDirectory`), so `--logfile /bad/path/app.log` does **not** fail. The residual failure
> modes are permission denied, a locked file, read-only media, path-too-long and disk full. Validating writability up
> front in `BumpSettings.Validate()` (with a probe, not a `Directory.Exists` check, which would reject currently valid
> paths) was evaluated and deliberately deferred: it cannot protect against failures that occur after validation, and
> it would need chaining through the four existing `Validate()` overrides.

If the user passes `--logfile /bad/path/app.log`, Serilog's file sink throws asynchronously at write time and the
failure is routed to `SelfLog` — which is only wired to `Debug.WriteLine` in DEBUG builds. A Release user gets no
console signal that their logfile was never created; the command still exits 0. This is not a regression (the previous
`ArgumentHandler`-based flow had the same behavior), but while the parsing responsibility was moved, it would have been
an easy place to improve signaling: `LoggerConfigurator.Configure` could catch/warn, or the interceptor could emit
`AnsiConsole.MarkupLineHintEscape` a one-line warning via `Log.Warning`-style console output when the file sink fails
(`Serilog` won't throw, so the practical option is a pre-check such as `Path.GetDirectoryName` + writability probe).

Low priority, and arguably out of scope for this branch — flagging so it isn't lost.

### 3. [Nit] `DelegatingLoggerTests` skips the nested `<Method>` grouping convention
`test/DotBump.Tests/Common/DelegatingLoggerTests.cs`

> **Resolution.** The facts now live under nested `IsEnabled`, `Write`, `Debug` and `ForContext` groups.
> `ForContext.Debug_With_ForContext_Forwards_Event_To_Active_Logger` calls
> `ForContext<DelegatingLoggerTests>().Debug(...)` through the `ILogger` interface and verifies the event reaches the
> active logger with `SourceContext` populated.
>
> For the record: in Serilog 4.4.0 the `ForContext` default implementation creates a new logger via
> `new LoggerConfiguration().WriteTo.Logger(this).CreateLogger()`, so the derived logger still writes through the
> delegating instance. The new test pins that guarantee rather than the implementation detail.

Per the repo's test conventions (and the sibling `LoggingInterceptorTests`, which uses a nested `public class
Intercept` group), each tested method gets a nested public class. Here the three facts live directly on
`DelegatingLoggerTests`. Suggest wrapping them in `IsEnabled`, `Write`, and `Debug` nested groups for consistency,
especially if more forwarding tests (see below) get added.

**Related coverage note:** the XML remarks document that *all* `ILogger` members funnel into `Write(LogEvent)` in
Serilog 4. That invariant is tested for `Debug(...)` but not for `ForContext` — the one member whose default
implementation returns a *new* logger rather than writing through the instance. If any production code or future
setup code calls `logger.ForContext<T>()` on the DI logger, that path deserves its own test
(`Debug_With_ForContext_Binds_And_Forwards_Event_To_Active_Logger`) before the comment's guarantee can be relied upon.

## Verified Non-Issues (checked, no action needed)

1. **DI ordering is safe.** Spectre creates the DI container, then parses/binds settings, then runs interceptors, then
   *resolves and creates* the command. Commands inject `ILogger` via primary constructors
   (`BumpSdkCommand.cs:12`), so they receive the `DelegatingLogger` and everything logged inside
   `ExecuteAsync` goes through the configured pipeline. The only things that cannot land in `--logfile` are
   Spectre-side parse errors and `--help`/`--version`, which never reach an interceptor — consistent with the intent
   documented in the remarks and README.
2. **Static logger swap is not a disposal hazard.** `DelegatingLogger` deliberately does not wrap a concrete logger, so
   the instance registered in the registrar is stateless and non-shared; `Log.CloseAndFlushAsync()` in `Program`'s
   `finally` flushes the real logger assigned by the interceptor. Swapping `Log.Logger` in tests does not leak sink
   handles because each test that triggers file sinks explicitly `Log.CloseAndFlush()` in its own `finally`.
3. **`DelegatingLogger` comments are factually correct for Serilog 4.4.0.** Verified against the 4.4.0 API surface: the
   `Debug`/`Error`/`Fatal`/... overload family and `BindMessageTemplate`/`BindProperty` are `virtual` (i.e., C# 8
   default interface implementations), leaving only `Write(LogEvent)` and `IsEnabled(LogEventLevel)` abstract. The
   `Debug_Binds_And_Forwards_Event_To_Active_Logger` test additionally pins the DIM indirection empirically, which is
   the part that would break if the Serilog DIM behavior ever changed.
4. **Test behavior coverage of old ArgumentHandler forms is preserved.** The deleted 254-line
   `ArgumentHandlerTests` exercised grammar-reproduction logic; by construction the equivalent behavior is now Spectre's
   own. `With_Logging_Syntax_Accepted_By_Spectre_Returns_0` still walks the previously problematic forms
   (`--debug true|false`, `--debug=...`, `--logfile app.log`, bare `--debug` before another option) at the real Spectre
   boundary, which is stronger evidence than parsing with a duplicate implementation.
5. **Static `Log.Logger` mutation in tests is safe *because* `xunit.runner.json` disables
   `parallelizeTestCollections`.** Each of `DelegatingLoggerTests` and `LoggingInterceptorTests` swaps the global
   `Log.Logger` with try/finally; this only works while collections run sequentially. If that setting is ever switched
   back on (or files move into different collections), these tests will race with each other. **Addressed as
   documentation:** `DelegatingLoggerTests`, `LoggingInterceptorTests` and `CommandConfigurationTests` now carry a
   class-level comment noting the dependency.
6. **No security concerns.** `--logfile` accepting arbitrary paths is expected CLI behavior; no credentials, network
   input, or file contents from user worktree data are newly handled by this change, and debug destructuring
   (with `[NotLogged]`/`[LogMasked]` attribute redaction) remains wired via `LoggerConfigurator.CreateConfiguration`.
7. **`Intercept` guards** `ArgumentNullException.ThrowIfNull` for both `context` and `settings`, and the
   `settings is not BumpSettings` early-return only fires for hypothetical future commands that don't inherit —
   acceptable since all current commands derive from `BumpSettings`.

## Conclusion

A clean lifecycle fix that removes duplicated command-line grammar handling and replaces it with Spectre's supported
extension point. The `DelegatingLogger` indirection is the right pattern given Spectre's container-before-interceptor
ordering, and the lifecycle-critical facts are documented where a future maintainer will read them (the remarks, not
just the commit message). Nothing here blocked the merge; findings 1 and 2 warranted a quick follow-up, while 3 and 4
were nits.
