# Code Review — branch `security-only`

**Date:** 2026-11-02
**Reviewer:** .NET Tech Lead review
**Scope:** Diff of branch `security-only` against `main` (commit `f5427a2` — *feat: bump SDK for missed security releases with --security-only*). 25 files, ~921 insertions / 179 deletions.

---

## Summary of the Change

The `--security-only` flag of `dotnet dotbump sdk` previously only bumped **when the newest indexed
release for the channel carried the `security: true` flag**. Because the index flag describes only
the *latest* release, a missed security release published before a non-security follow-up release
was never detected and no bump happened.

This change reworks the flag semantics:

- `ReleaseFinder` is now purely a candidate selector — the `securityOnly` parameter was removed from
  `TryFindNewRelease` (and from `BumpDockerHandler`'s call accordingly).
- `BumpSdkHandler` applies the security policy after candidate selection: when the candidate is not
  flagged as security, it dereferences the channel's `releases.json` link (new `Release.ReleasesJson`
  property), fetches the channel release history via the new `IReleaseService.GetChannelReleasesAsync(Uri)`
  and consults the new `ISecurityReleaseEvaluator` / `SecurityReleaseEvaluator`.
- The evaluator accepts the bump only when some SDK version inside a `security: true` channel release
  falls in the range `(currentSdkVersion, targetSdkVersion]`.
- `ReleaseWebService` now receives an `HttpClient` via constructor injection (registered once per
  command run in `CommandConfiguration`) instead of instantiating one per call, with the fetch logic
  consolidated into a private `GetJsonAsync(Uri)` helper.
- New DTOs (`ChannelReleases`, `ChannelRelease`, `ChannelSdk`) model the channel history document.

## What Was Done Well

- **Single Responsibility**: extracting the security policy out of `ReleaseFinder` is a clean
  decomposition. `TryFindMinorOrPatch`, `TryFindPatch` and `TryFindMajor` are all simpler now, and
  the candidate-selection vs. policy separation is reflected in a dedicated
  `ISecurityReleaseEvaluator` interface, which keeps `BumpSdkHandler` testable with a mock rather
  than driving it through handcrafted channel payloads everywhere.
- **HttpClient lifetime**: replacing the per-call `new HttpClient()` (with its ReSharper
  suppression) with a constructor-injected instance resolves the "ShortLivedHttpClient" smell
  properly rather than suppressing it.
- **Feature-band-aware design**: evaluating *every* SDK of *every* security release instead of only
  the newest release correctly handles the case where a user sits on an older feature band of the
  same channel (e.g., current `10.0.402`, security release shipped `10.0.403` and `10.0.113`).
  The test `With_Security_Release_In_Only_A_Lower_Feature_Band_Returns_False` documents this
  subtlety explicitly — good.
- **XML doc comments** on the added members (e.g., the "channel-level security flag only describes
  the newest release" note on `TryKeepSecurityReleaseAsync`) explain the *why*, not just the what.
- **Fail-closed behavior**: when the channel history cannot be fetched under `--security-only`, the
  command fails rather than silently skipping a possibly-needed security bump. This is intentional
  and covered by `With_SecurityOnly_True_And_Channel_Releases_Unavailable_Throws`.
- **Tests**: new test data is offline JSON under `Data/` with the existing
  `FakeHttpMessageHandler` reused — consistent with the repo's testing guidelines. Telemetry-light
  naming (`With_No_Missed_Security_Release_Does_Not_Bump`), Shouldly assertions, Moq `Verify` for
  interaction checks (`GetChannelReleasesAsync` never called when the index flag is already
  security) all follow the canonical patterns.

## Findings

### 1. [Medium] Deserialization exceptions from channel history are not translated into `DotBumpException`, and malformed versions degrade silently

`src/DotBump/Commands/BumpSdk/SecurityReleaseEvaluator.cs`,
`src/DotBump/Commands/BumpSdk/DataModel/ChannelSdk.cs`,
`src/DotBump/Commands/BumpSdk/ReleaseWebService.cs`

Two related robustness gaps in the new code path:

a) `ChannelSdk` eagerly constructs a `SemanticVersion` from the `version` field during record
initialization:

```csharp
internal record ChannelSdk([property: JsonPropertyName("version")] string Version)
{
    public SemanticVersion SemanticVersion { get; } = new(Version);
}
```

While `SemanticVersion`'s constructor tolerates unparsable *formats* (it degrades to `0.0.0` with
`IsValid == false`), a **missing or empty** `version` element in the upstream `releases.json` payload
throws `ArgumentException` inside the `System.Text.Json` pipeline inside
`ReleaseWebService.GetChannelReleasesAsync` (`JsonSerializer.Deserialize<ChannelReleases>(json)`).
Unlike `GetJsonAsync` (which logs and rethrows network failures with the failing URI in context),
deserialization failures escape as raw `JsonException` and hit the catch-all in `BumpSdkCommand`,
losing the "which channel document failed" context. Suggest wrapping the deserialization in the same
style used elsewhere:

```csharp
ChannelReleases channelReleases;
try
{
    channelReleases = JsonSerializer.Deserialize<ChannelReleases>(json);
}
catch (JsonException exception)
{
    logger.Error(exception, "Invalid channel releases payload from {Uri}", channelReleasesUri.ToString());
    throw new DotBumpException($"Invalid release history payload from {channelReleasesUri}.");
}
```

The same treatment is worth considering for `GetReleasesAsync` for consistency, though that path is
pre-existing.

b) When an SDK entry has a *valid XML shape but unparsable version format*, `SemanticVersion`
silently degrades to `0.0.0` (`IsValid == false`), and the `version > currentVersion` filter in
`SecurityReleaseEvaluator` drops it without any log line. A mis-typed upstream version would
therefore cause `--security-only` to *skip a needed security bump silently* — arguably the exact
failure mode this feature exists to prevent. Suggest logging when the candidate SDK version is
invalid, at minimum at Debug level:

```csharp
var securityVersion = channelReleases.Releases
    .Where(release => release.Security)
    .SelectMany(release => release.Sdks ?? [])
    .Select(sdk => (sdk.SemanticVersion, sdk.Version))
    .Where(candidate => !candidate.SemanticVersion.IsValid
        ? LogInvalidAndExclude(candidate.Version)
        : candidate.SemanticVersion > currentVersion && candidate.SemanticVersion <= targetVersion)
    ...
```

(or a plain two-step loop with a `logger.Debug` on `!IsValid`). Under `--security-only` this data
drives a security decision, so it should not disappear without a trace.

### 2. [Medium] Channel history URL is accepted from the index payload without host validation

`src/DotBump/Commands/BumpSdk/BumpSdkHandler.cs`

`TryKeepSecurityReleaseAsync` accepts any absolute URI coming out of the release index:

```csharp
if (!Uri.TryCreate(newRelease.ReleasesJson, UriKind.Absolute, out var channelReleasesUri))
{
    throw new DotBumpException(
        $"Release metadata for .NET {newRelease.ChannelVersion} does not link a release history URL.");
}
```

The value originates from a trusted Microsoft feed, so the practical risk is low, but the tool makes
a network request to whatever URI the upstream XML declares. If the index is ever compromised or
redirected, `dotbump` becomes a fetch-and-follow vector whose requests now include an attacker-
chosen URL on every machine running the tool. A cheap hardening is to constrain the parsed URI to
the expected origin:

```csharp
private const string RequiredReleaseHost = "builds.dotnet.microsoft.com";

if (!Uri.TryCreate(newRelease.ReleasesJson, UriKind.Absolute, out var channelReleasesUri)
    || channelReleasesUri.Scheme != Uri.UriSchemeHttps
    || !string.Equals(channelReleasesUri.Host, RequiredReleaseHost, StringComparison.OrdinalIgnoreCase))
{
    throw new DotBumpException(
        $"Release metadata for .NET {newRelease.ChannelVersion} links an unexpected release history URL: {newRelease.ReleasesJson}");
}
```

If you'd rather not hard-code the host, at minimum enforce `https` and reject credentials embedded
in the URI (`channelReleasesUri.UserInfo.Length > 0`). Note the equivalent concern exists for the
upstream fetch itself (a compromised feed could steer behavior); this change only widens the attack
surface by one degree, so this is a hardening suggestion rather than a blocker.

### 3. [Minor] `TryKeepSecurityReleaseAsync` does not trace method boundaries (`MethodStart` / `MethodReturn`)

`src/DotBump/Commands/BumpSdk/BumpSdkHandler.cs`

Every other method in the touched code path (`HandleAsync`, `TryFindNewRelease`,
`IncludesNewerSecurityRelease`, `GetChannelReleasesAsync`) logs `logger.MethodStart` and
`logger.MethodReturn` per the project's logging conventions; this new private method does not. This
matters here in particular because the method is the decision point for the security flag — a
debug log of its entry/exit including the resolved outcome ("kept", "dropped", "threw") pairs well
with the two existing `logger.Debug` lines. Add:

```csharp
public async Task<Release?> ... // in TryKeepSecurityReleaseAsync:
logger.MethodStart(nameof(BumpSdkHandler), nameof(TryKeepSecurityReleaseAsync));
...
logger.MethodReturn(nameof(BumpSdkHandler), nameof(TryKeepSecurityReleaseAsync), result);
```

### 4. [Minor] `Try*` naming without a `bool` return

`src/DotBump/Commands/BumpSdk/BumpSdkHandler.cs`

`TryKeepSecurityReleaseAsync` returns `Task<Release?>` rather than the `bool`/`out` pattern the
`Try` prefix conventionally signals (cf. `TryFindNewRelease`, itself a bit of a stretch). A name such
as `ResolveSecurityReleaseAsync` or `EvaluateSecurityReleaseAsync` communicates "keep or discard the
candidate" without borrowing the Try-idiom. Cosmetic — the current name is understandable.

### 5. [Minor] Test fake ignores the requested channel URI

`test/DotBump.Tests/Commands/BumpSdk/Fakes/ReleaseFileService.cs`

```csharp
private readonly string _channelReleasesPath = Directory.GetCurrentDirectory() + "/Data/releases-8.0.json";
...
public async Task<ChannelReleases> GetChannelReleasesAsync(Uri channelReleasesUri)
{
    // the argument is not used at all
```

`GetChannelReleasesAsync` always returns `releases-8.0.json` regardless of which channel the index
points at. Today the two command-level `SecurityOnly` tests both target the 8.0 channel so this
works, but a future test that bumps from, say, 9.0.200 would silently get 8.0 channel data and
produce misleading (or even confusingly-failing) results. Suggest making the fake fail loudly on
mismatch, or deriving the data file from the URI's channel segment:

```csharp
public Task<ChannelReleases> GetChannelReleasesAsync(Uri channelReleasesUri)
{
    ArgumentNullException.ThrowIfNull(channelReleasesUri);
    var channelVersion = channelReleasesUri.Segments[^2].TrimEnd('/');
    var path = Path.Combine(Directory.GetCurrentDirectory(), "Data", $"releases-{channelVersion}.json");
    if (!File.Exists(path))
    {
        throw new DotBumpException($"No test data for channel releases '{channelReleasesUri}'.");
    }
    ...
}
```

(or simply `channelReleasesUri.ToString().ShouldContain("/8.0/")`-style guard-throw if full mapping
feels like overkill for a fake).

### 6. [Minor] Logging parameter names diverge from the values they carry

`src/DotBump/Commands/BumpSdk/BumpSdkHandler.cs`

```csharp
logger.Debug(
    "Bumping to {TargetVersion} includes a security release newer than {CurrentVersion}",
    newRelease.LatestSdk,
    currentSdk.Version);
```

`{TargetVersion}` is bound to `newRelease.LatestSdk` (the raw string, not the `SemanticVersion`
string) while elsewhere the codebase logs `SemanticVersion.ToString()`. Not a defect — the message
is still coherent — but naming the template placeholders to match the values they receive (or using
`newRelease.LatestSdkVersion.ToString()`, mirroring `currentSdk`'s version) would make
searching/debug output consistent.

### 8. [Info] Intentional semantic scoping of `--security-only` under Major bumps — worth documenting

`src/DotBump/Commands/BumpSdk/BumpSdkHandler.cs`

When `--security-only` is combined with `major`, only the *target channel's* history is consulted
(for example, bumping 8.0.x → 9.0 checks `9.0/releases.json`). A missed security release that
remains within the user's *current* channel (e.g., 8.0.405 published while they sit on 8.0.400) does
not, by itself, justify a major bump to a newer non-security channel — and the patch-level security
fix inside that missed release does propagate into the channel fix already. This is a defensible
interpretation, agrees with how the pre-existing behavior was scoped, and the updated help text on
`BumpSdkSettings` ("Only bump the version if a security release newer than the current SDK version
exists") reasonably captures the intent. No code change required; flagging in case you want the
channel-scoped nuance captured in the command help or README later.

## Test Coverage Assessment

Coverage of the new logic is good:

- Evaluator: security in/before/after the `(current, target]` window, absence of security releases,
  empty releases, lower-feature-band-only security, `Sdks == null` tolerance, null-argument guard
  — the boundary cases that matter (`current == target`, exact boundary `version == targetVersion`
  counting as *included* via `<=`) are exercised.
- Handler: index-flagged security short-circuit (no second request — verified by interaction),
  bump when evaluator says yes, no-bump when evaluator says no, missing `ReleasesJson` →
  `DotBumpException`, network failure → propagate + file not written (fail-closed on disk too).
- Service: real payload parsing, empty payload, missing `releases` property, null URI guard.
- Command: end-to-end through `ExecuteAsync` against the offline `releases-index.json` +
  `releases-8.0.json` pair, asserting both the file outcome (`8.0.400 → 8.0.406`) and the console
  report (`sdk: 8.0.400 > 8.0.406`).

The deleted `ReleaseFinder` security-only tests were removed because the responsibility moved up
into the handler/evaluator, which are now covered; no coverage was lost.

One overall gap: the happy-path CLI test (`With_SecurityOnly_True_And_Missed_Security_Release_Bumps_To_Latest`)
exercises the 8.0 channel, which relies on the fake channel-URI behaviour called out in Finding 5.

---

## Verdict

The change is well designed for its purpose, and the implementation follows the repository's coding
and testing conventions closely. The two Medium findings (deserialization robustness / silent
treatment of invalid versions in the security decision path, and the unguarded outbound URI) are
worth addressing in this branch since `--security-only` is precisely the mode where silent
misses are most damaging; the remaining items are polish.
